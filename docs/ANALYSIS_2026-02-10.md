# rad.io Project Analysis (2026-02-10)

## Executive Summary
rad.io is a **browser-based Software-Defined Radio (SDR) visualizer and controller** aiming to be a professional-grade tool accessible directly via the web. It is currently in the **Pre-Alpha / Product Definition** phase (Phase 0/1). The project emphasizes engineering rigor, reproducibility, and a modern user experience over quick-and-dirty implementation.

**Key Differentiator:** "Professional-grade" via the browser. It targets serious hobbyists and professionals who need calibrated measurements, stable recording, and reliable hardware control without installing native desktop software.

**Current State:**
- **Code:** Skeleton structure exists (Node/TypeScript/React likely, based on roadmap hints), but core DSP and device logic is nascent.
- **Documentation:** Extremely detailed and high-quality product definition. The roadmap is exhaustive, covering everything from "UX contracts" to "DSP pipeline architecture."
- **Infrastructure:** Version control and basic tooling are present, but the CI/CD pipeline and automated testing harness described in the roadmap are likely todo.

## Technology Stack (Inferred & Planned)
- **Runtime:** Web Browser (Chrome/Edge focused due to WebUSB/WebAudio requirements).
- **Languages:** TypeScript (Strict), WebAssembly (AssemblyScript/Rust for DSP - TBD).
- **Core Web APIs:**
  - **WebUSB:** Direct hardware access (HackRF, RTL-SDR).
  - **WebAudio / AudioWorklet:** Low-latency audio processing.
  - **Web Workers:** Off-main-thread DSP.
  - **SharedArrayBuffer:** Zero-copy data passing.
  - **WebGL / WebGPU:** High-performance spectrum/waterfall rendering.
- **Data Persistence:** IndexedDB (Recordings, Settings).
- **Interchange Formats:** SigMF (Signal Metadata Format) for recordings.

## Project Structure & Organization
- `docs/roadmap/`: **The Crown Jewel.** A massive, structured breakdown of every feature, risk, and architectural decision.
    - `00_PRODUCT_DEFINITION`: Requirements, UX contracts, ADRs (Architecture Decision Records).
    - `01_FOUNDATION_...`: Tooling, telemetry, diagnostics.
    - `02_DETERMINISTIC_SOURCES`: Testing harness (mock/file sources).
    - `03_CORE_DSP_PIPELINE`: The actual radio processing logic.
    - ... and so on up to Phase 9.
- `package.json`: Minimal dependencies so far; indicates early stage.
- `.github/`: CI/CD workflows (likely basic).

## Key Components (Planned)
1.  **DSP Pipeline:** A directed graph of processing nodes (Source -> DDC -> Demod -> Sink).
2.  **Device Abstraction Layer (`ISDRDevice`):** Unified interface for WebUSB devices and Mock/File sources.
3.  **Visualization Engine:** 60FPS canvas/WebGL renderer for Spectrum and Waterfall.
4.  **Telemetry & Diagnostics:** "Flight recorder" for USB health, buffer underruns, and DSP latency.
5.  **Session Management:** State persistence, "safe mode" recovery, and reproducible bug reporting.

## Strengths
- **Vision:** Crystal clear. The roadmap explicitly calls out "Success Gates" and "Irreversible Decisions."
- **Rigor:** Focus on "contracts" (UX, Data, DSP) ensures components will fit together.
- **Testing:** Heavy emphasis on deterministic testing (Mock/File sources) before hardware integration.

## Weaknesses / Risks
- **Complexity:** The ambition is huge. Implementing a stable, low-latency DSP pipeline in JS/WASM is non-trivial.
- **Browser Limits:** Reliance on WebUSB limits support to Chromium-based browsers; garbage collection pauses could impact audio stability.
- **Early Stage:** No working prototype evident in the file list yet (just docs/config).

## Immediate Next Steps (Per Roadmap)
1.  **Vertical Slice A:** Build a mock source -> FFT -> Audio path (no hardware).
2.  **WebUSB Bring-up:** Get a HackRF or RTL-SDR streaming raw samples to a worker.
3.  **ADRs:** Finalize decisions on Worker Topology and SharedArrayBuffer strategy.
